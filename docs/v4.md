# V4 additional tests

[Repository overview](../README.md) · [Full proposed study](protocols/BENCHMARK_V4_PLAN.md)

V4 adds experiments that address the Reddit questions about open-source alternatives, AutoML, generalization beyond familiar holdouts, and iterative decisions. **The V3 benchmark is complete and is not repeated.** Its published scores remain historical context. Read the [feedback-to-test mapping](protocols/BENCHMARK_V4_PLAN.md#reddit-feedback-to-experiment-mapping) for the complete proposed study.

The current runnable scaffold covers **new support-policy pairs** and produces two separate notebooks: Jev and local models. Both embed the same frozen inputs and can run in parallel. The policy data is a synthetic development draft requiring review. Temporal/AutoML and iterative-feedback experiments remain planned; this scaffold does not yet answer all the comments.

## What is implemented

- A common decision request for Jev, Von, and routed Laya, with all class IDs and descriptions retained in order.
- Pinned local SDK source and checkpoint revisions, per-request Laya routing, device records, and input audits before local inference.
- New paired cases for negation, exceptions, event order, and paraphrases; whole-pair partitions and held-out combinations of edits and rule context, with new wording. Individual facts can recur across families. Labels come from an executable refund policy; hidden facts and labels never enter provider requests.
- Separate training, model-selection, policy, and test partitions, frozen manifests and input hashes. Both notebooks use byte-identical snapshots and case IDs.
- Resumable per-case predictions, provider-specific caches, attempt logs, bounded retries, and request/time ceilings. Cache keys include run identity and caller context; `use_cache=False` bypasses both cache reads and writes.
- Optional majority and TF-IDF/linear SVM comparators fitted on the **new task**. The existing tabular helpers remain available for future tasks and optional continuity diagnostics. Model selection uses development data only.
- Raw accuracy, balanced accuracy, macro-F1, per-class recall, native-probability Brier/log loss, probability coverage, and uncached latency percentiles. Failures and unsupported inputs remain in the operational denominator.
- Both-members-correct pair rate, with family/composition breakdowns; failures count against pair success.
- An offline regression suite and two self-contained Kaggle notebook workers. The local notebook runs Von and Laya concurrently on separate T4 GPUs, with per-process CUDA isolation, hardware checks, logs, and peak-memory records. Export recomputes each summary; merge rejects differing studies, data, pair metadata, or conflicting files.

The implementation is in `jevbench_v4/`; frozen `jevbench/`, published tables, notebooks, and bundles remain unchanged. The default V4 preparation generates only the new policy cases and downloads no old dataset. No V3 aggregate score is treated as a paired V4 observation.

## Run the offline tests

```bash
python -m pip install -r requirements-dev.txt
python -m tests.validate_v4
python -m tests.validate_v3_artifact
```

The V4 suite blocks the Requests transport and uses synthetic data, fake provider transports, and small real CPU model fits. It does not load credentials, download weights, or call Jev. GPU/SDK execution needs the compatibility pilot on Kaggle; passing these tests does not establish local-model accuracy or CUDA compatibility.

## Build the two Kaggle notebooks

```bash
python -m scripts.build_v4_notebook
```

This creates:

- `generated/jev_benchmark_v4_jev.ipynb`: Jev API worker; a CPU session is sufficient, with Internet and `TYPESAFE_API_KEY` in Kaggle Secrets.
- `generated/jev_benchmark_v4_local.ipynb`: Von/Laya and optional new-task ML comparators; use a GPU session. No Jev secret is needed.
- `generated/jev_benchmark_v4_source.zip`: the common source, test suite, and prepared study embedded identically in both notebooks.

Upload the two notebooks to separate Kaggle sessions and run them in parallel. Select **two T4 GPUs** for the local notebook: **Von uses GPU 0 and Laya uses GPU 1 simultaneously**. The notebook refuses to start its local workers unless both GPUs are available. Each notebook verifies the common study and writes to its own output root. Install dependencies before inference. Both notebooks start with model switches disabled. `RUN_EVALUATION` is separate from the development pilot; `RUN_NEW_TASK_BASELINES` never invokes the old V3 benchmark.

Each model process sees only its assigned GPU through `CUDA_VISIBLE_DEVICES`, so both use the logical name `cuda:0` inside their isolated process. The recorded parent index and visibility selector identify the actual assignment. Each GPU must hold its own model; the cards' memory is not pooled. Before loading models, each worker tests an FP16 matrix multiplication on CUDA. Audits check model tensor placement and reject CPU fallback, including Laya fallback during inference. [PyTorch CUDA environment variables](https://docs.pytorch.org/docs/2.14/cuda_environment_variables.html)

The launcher allocates two CPU threads per GPU worker by default and imposes no API pacing delay on local inference. CPU comparators run after the GPU jobs. `execution/local/` contains the immutable device plan, separate provider logs, exit statuses, and successful-worker peak-memory records; these are preserved in exports and merged artifacts. A worker failure or notebook interrupt stops its sibling. A run lock prevents duplicate launchers from writing the same provider ledgers. After an abrupt session kill, remove a stale `.lock` only after confirming its old workers are stopped; ordinary failures release it automatically.

The previous generated single `jev_benchmark_v4_pilot.ipynb`, if present from an earlier build, is superseded. The builder preserves it and refuses to overwrite either new notebook if it contains saved outputs.

The default pilot snapshot has 80 training, 32 selection, 32 policy, and 64 test observations. Provider compatibility uses 50 **training-partition** cases (25 whole pairs). Its summaries are labeled `development-pilot`. The larger `--preset study` build uses 1,200/320/320/1,200 observations; it is still a draft, not a reviewed protocol. Collecting policy predictions does not yet implement threshold adjustment.

## Command-line workflow

From the repository root, using Python 3.12+ for the local SDKs:

```bash
python -m scripts.run_v4 prepare --root results/v4_pilot --preset pilot
python -m pip install -r requirements-v4-local.txt
python -m scripts.run_v4 local --root results/v4_pilot --phase pilot --gpus 0 1 --min-gpus 2
python -m scripts.run_v4 pilot --root results/v4_pilot --provider jev
python -m scripts.run_v4 export --root results/v4_pilot
```

`prepare` generates the new support-policy task offline. Local-provider pilots download the pinned weights. The Jev command makes real API calls. Single-provider commands run only the named provider. Inspect `data/Support_Policy/review_sample.csv` in the prepared root for draft labels and rendered observations.

The `local` command selects both Von and Laya. Use `--phase evaluate` for the new policy/test partitions. Omitting `--gpus` discovers available devices, and the CLI's default minimum of one permits sequential model processes on a single GPU. The generated Kaggle notebook explicitly requires two. Changing the assignment or CPU thread budget requires a fresh run root. Direct `pilot --provider NAME --device DEVICE` remains available for individual diagnostics.

`baselines` fits majority and SVM on the new policy task; `evaluate --provider NAME` evaluates complete policy and test partitions. Changing source, configuration, provider identity, package environment for a job, or request budgets requires a new run root. Keep development pilots and final reviewed study runs separate.

Download both result ZIPs and extract each into its own directory. Combine completed workers without rerunning inference:

```bash
python -m scripts.run_v4 merge --root results/v4_combined --inputs path/to/jev_run path/to/local_run
```

The destination must be new. Merge requires matching run manifests, source fingerprints, data files, and split IDs. It verifies per-case predictions and recomputes tables, then creates `results/v4_combined_results.zip`. Use the same source version that built both notebooks; each exported archive includes that source. Different notebook package environments are recorded per worker and do not require identical hardware.

The defaults are 50,000 request attempts per provider, two retries for transient service/transport failures, a 0.15-second minimum interval for Jev (zero for local models), and a 7,200-second elapsed-time ceiling per provider. Override with `--max-attempts`, `--min-interval`, and `--max-seconds` before starting a run. Attempt counts and elapsed time recorded in the ledger survive resumes. A running request/model call can finish after the time ceiling; this is not process preemption. No inherited V3 monetary estimate cap is applied.

## Provider compatibility details

| Provider | Pinned implementation | Input handling |
|---|---|---|
| Jev | `jev-1.13.0`, response model checked | Full JSON request; remote tokenizer behavior is unverified |
| Von | SDK commit `bed7e7337791c5124a557eb59ad918cb6747b276`; `wfzyx/von-1.0` revision `94f220771d119201634d1fdd734ce7382b2c185b` | Current default pairwise backend; every pair must fit its 512-token limit |
| Laya | SDK commit `42626c348753fbb17572a813127df2278a1ec527`; `convaiinnovations/laya` revision `1c5edc17a7acd8701df6fc341c0d179f1c62c982` | Default router with task detection disabled; every packed token and option marker must match the complete representation |

These contracts were checked against the pinned [Von backend source](https://github.com/wfzyx/von/blob/bed7e7337791c5124a557eb59ad918cb6747b276/src/von/backends/berta_backend.py), [Laya packing source](https://github.com/NandhaKishorM/laya/blob/42626c348753fbb17572a813127df2278a1ec527/laya/common.py), [Laya router](https://github.com/NandhaKishorM/laya/blob/42626c348753fbb17572a813127df2278a1ec527/laya/router.py), and [TypeSafe response documentation](https://docs.typesafe.ai/introduction/quickstart). Dependency pins are for the compatibility pilot; freeze the complete Kaggle environment after testing it.

The harness does not shorten inputs or remove choices to force a result. Laya's SDK can trim descriptions while retaining their option markers, so checking marker count alone is insufficient. Unsupported rows are explicit, probability metrics state their successful-row coverage, and missing true classes yield an undefined balanced accuracy rather than a misleading pilot score.

Von's default backend is explicitly named `sdk-default-pairwise`. Its separate option-marker backend is not substituted based on its advertised timings. Laya's default router records which checkpoint it selected. A requested GPU run fails if the SDK moves to CPU; that result cannot be reported as GPU performance. No speed or quality conclusions have been measured here. Concurrency tests use real child processes with simulated GPU inventories; they do not establish dual-T4 model compatibility, which still needs the Kaggle development pilot.

## Remaining study work

The [proposed V4 study](protocols/BENCHMARK_V4_PLAN.md) remains authoritative for the intended experiment. This stage does **not** yet implement frozen sentence embeddings, AutoGluon, supervised threshold/coverage policies, paired uncertainty intervals, temporal windows, or the support simulator and loop controls. It also does not establish GPU compatibility, complete synthetic-label review, or freeze a publication-ready V4 protocol.

Next: review/expand the policy cases and add the embedding comparator; implement future-only temporal evaluation with AutoML; implement iterative support decisions and the four control conditions; add paired uncertainty and freeze all three tracks before the full study. Keep failures visible; do not select the final population based on which model succeeded on it.

## Retained optional continuity helpers

The earlier three-dataset continuity code and its regression tests are preserved. Using it requires explicit `--suite continuity` for preparation and execution; the new notebook builder never selects it. The CLI rejects an old-dataset run root unless this suite is explicitly named. It is outside the current V4 plan and should not be run as part of the additional study.
